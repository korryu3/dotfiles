# PRレビューコメントの文体規範

ユーザー名義でPRレビューコメント・返信を代筆するときは、以下の規範に従う。

## 適用条件

- **適用する**：他人のPRへユーザー名義で指摘・質問を書くとき。自分のPRに来た他人のレビューへユーザー名義で返信するとき
- **適用しない**：ユーザー自身に向けたコメント（セルフレビュー、Claude名義の自動レビュー投稿）。Claude名義の投稿は呼び出し元スキルの書式に従う
- **レジスタ判定**：仕事のリポジトリ（組織リポジトリ）では敬体。個人・友人のリポジトリではタメ口（「〜だね」「〜しといてね〜」）。迷ったら敬体

## 大原則

- 文末は「。」より「！」が既定。依頼・報告・同意・感謝は「！」で締める（「〜いただきたいです。」と句点で終えない）
- **診断はヘッジ、要求は明確に**。現象・原因は「〜そうです」「〜な気がします」「〜かもです」で推量にとどめ、してほしいことは「〜して欲しいです！」とはっきり言う。強制度を伝えるのは述部のヘッジではなく要求動詞
- **断定するのは自分が確実に把握していることだけ**。ドキュメントの受け売りや検証してみた結果は「〜みたいです！」「〜っぽいです！」で伝える
- 一人称は「私」。「自分としては」と書かない
- 相手と共有しているコンテキストを説明し直さない。括弧書きの補足説明も、相手が知っている内容には付けない。指摘は相手に伝わる最小限の長さでよく、自明な修正は一言＋suggestionで足りる
- 要望には理由を「〜ので、〜」で添える。理由を省いてよいのは機械的で自明な修正（コンフリクト解消、既存箇所と同様の対応）だけ
- 一文一改行。段落（空行）は長文のときだけ
- 長さは1〜3行が基本。長文になるのはバグ報告・設計議論のときだけ
- 不確かさ・言いよどみは「、、」で表す（三点リーダー「…」は使わない）。困惑を含む疑問は「〜ですかね、、？」

## ラベル

- ラベルは**他人のPRへのインライン指摘のスレッド先頭でのみ**使う。返信・PRサマリ・スレッド途中では使わない
- 種類と使い分け：
  - `[ask]`：変更要求を伴わない純粋な質問・意図確認。ほぼ疑問文で終える
  - `[nit]`：軽微で具体的な修正依頼（命名、重複の共通化、些細な漏れ）。過去には`[nits]`表記もあるが、現在は単数形`[nit]`に揃える
  - `[imo]`：任意度の高い設計意見。判断は相手に委ねるトーン
  - `[must-fix]`：実際に挙動が壊れる指摘。必ず具体的な破壊シナリオを添える
- 表記は半角角括弧・小文字。**ラベルは単独行に置き、本文は改行してから始める**
- ラベルは必須ではない。普通の修正依頼（デフォルトの重要度）には付けず、デフォルトから外れるとき（質問だけ・些末・意見・ブロッカー）に付ける。**迷ったら付けない**（付けないコメントの方が多数派）

## 指摘コメントの構成

- コメント単位では結論先。**最初の1〜2文で「何をしてほしいか」が伝わる**ようにする
- 文単位では根拠先。理由と要望を「〜ので、〜したいです！」と一文に融合する形が基本形
- 一文に収まらないときの順序は「ラベル→指摘・要望→理由→提案・例」。理由を後置するときの書き出しは「今のままだと〜」「現状だと〜」「というのも〜」
- 既存コードとの比較を根拠にする（「v1だと〜なので」「`backend/`と同じように〜」）
- コード識別子（関数名・ファイル名・変数名）はバッククォートで囲む
- 参考URLは裸のまま独立行に置く。「参考:」ラベルは付けても付けなくてもよい
- 同じ指摘が複数箇所にあるときは、1箇所にまとめず該当行ごとに同文を貼る（「こちらも同様の対応をお願いします！」）

## suggestionブロックとコード例

- ```suggestion```はそのまま適用できる確定修正のときだけ使い、必ず説明文の後に置く
- 削除の提案は空のsuggestionブロックで行う（「これ不要だと思います！」＋空ブロック）
- 設計レベルの提案コードはsuggestionではなく```python```等のフェンスで「イメージ：」「例：」として貼る。叩き台であることが伝わる形にする
- 重要度の高い指摘ほどsuggestionは付けない（設計判断を相手に委ねるため、コードスケッチにとどめる）

## 強制度のグラデーション

- 強（必須級）：「〜して欲しいです！」「〜していただきたいです！」「〜お願いします！」
- 中（強い提案）：「〜したいです！」「〜した方がいいと思います！」
- 弱（任意提案）：「〜でもいいかもです」「〜な気がします」「〜かなと思いました！」
- 判断保留：「〜いかがでしょうか？」と疑問形で相手に返す
- 命令形「〜してください」は使わない
- 「お任せします」「対応不要です」「どちらでもいいです」と明文で免除しない。任意性は`[imo]`・「かもですね」・括弧書き（「（〜は稀だと思いますが）」）・「将来的に〜」で伝える
- 願望形「〜したいです！」を積極的に使う。コードを共同所有物として扱う一人称
- must-fix級は「期待と実際」「壊れるメカニズム」「放置した場合の影響」を書いて長文化してよい。それでも診断部は「〜になりそうです」と推量にとどめる

## 質問の型

- 意図・理由を問う標準形：「なぜ〜なのでしょうか？」「どういう意図なのでしょうか？」
- 軽い確認・仮説の投げかけ：「〜ですかね？」
- 自分の案はあるが確信がないとき：「〜でいいんじゃないですかね、、？」と案を出しつつ疑問形に流す
- 認識合わせ：自分の理解を先に言語化して「〜という認識で合ってますか？」とYes/Noで答えられる形にする
- 詰問と誤読されそうなときは「純粋な疑問なんですが、」を前置きするか、理由を自分に帰属させる（「〜の挙動がわかっておらず、、」）
- 「私の理解不足かもですが」という定型は使わない。「〜がわかっておらず、、」の中断形を使う

## 返信の執筆手順

自分のPRに来たレビューへ返信するときは、まず相手のコメントを読み、次のどれかを判断してから書く：**同意して対応／対応報告／反論・見送り／質問返し／事実回答**。

- 返信にはラベルを付けない
- 複数論点への返信は相手の文を「> 」で引用して各個回答する
- 議論→対応→報告は1コメントに詰めず、別コメントに分けて連投してよい

### 同意して対応

短い同意フレーズ＋「修正します！」の2文構成。同意フレーズは「確かに」「おけです！」「承知です！」「ですね！」。即断できないときは「試してみます！」「調べてみます！」の試行宣言にする。

### 対応報告

「対応しました！」または「修正しました！」＋commit hash。hashは前置きでも後置きでもよい。複数コミットは箇条書き（`- <hash>`）。

- hashと前後の文字は半角スペースで区切る（「<hash> で修正しました！」）。前の文字と連続するとGitHub上で自動リンクにならないため
- hashをバッククォートやコードブロックで囲まない。囲むとリンク化されないため

### 反論・見送り

結論を先に出し、理由を「〜ので」で後置する。和らげ方：

- 部分的譲歩を先に置く（「おっしゃる通り〜ですが、」）
- 根拠として公式ドキュメントURL・実測出力・過去PRリンクを添える
- 見送りはスコープ外宣言（「このPRの責務ではないので、別途対応します！」）や別Issue化で着地させる
- 対応不要と主張するときも代替案・妥協案を添えることが多い
- 相手が引かず自分が従うと決めたら「承知です 🫡」「現実装で進めます！」で明示的にクローズする。従った後でも「後学のために、お手隙で良いので〜の意図をお聞きしたいです 👀」と学習質問を残してよい

### 質問返し・事実回答

- 質問返しは相手の意図を自分の言葉で言い換えて「〜ということでしょうか？」
- 事実回答は結論一語の即答＋補足（「です！」「必須じゃないです！＋理由」）
- 教わったときのリアクションは素直に感嘆する。「なるほど！」＋「理解しました！」＋「ありがとうございます！」の三点セットや、「そんなことできるんですね！勉強になります！」の型。感謝単体で終わらせず次アクションを添える
- 「勉強になります！」を使うのは納得・学びが完了したときだけ。これから疑問や反論を続ける文脈では使わない
- 気づき・納得の瞬間は感嘆詞から入る短文で書く。書き出しは「あ、」「あー」「！なるほど！」「お！」。納得は「なるほど！」「理解しました！」（強い納得は「なるほど！！」）、相手への同意を含むなら「確かに〜ですね」「あ、おっしゃる通り〜ですね」。「なーるほど、完全に理解しました。」のような伸ばし表現も使う
- 自己訂正・独り言は常体のまま書く（「あ、いやだめだ」調）。句点や「、、、」で終えてよく、きれいな敬体に整え直さない

## 絵文字

- 使うのは👀（軽い指摘・意見聞きたい）、🙏（依頼）、🤔（思案・自信低）、🫡（承知）、🙇‍♂️（負荷をかける依頼）に限る
- 位置は文末。絵文字の前に半角スペースを入れる（「〜な気がします 👀」）
- 頻度は1割程度。**付けないコメントが大多数**。1コメント1個まで

## やらないこと（AI文体からの逸脱防止）

- 太字セクション見出し（「**理由**:」「**提案**:」「**期待**:」）でコメントを構造化しない
- 網羅的な箇条書き・整然としたセクション分割をしない。長文でも構成は思考順
- 「です。」で統一された「！」ゼロの均質な敬体長文を書かない
- 「ご確認のほどよろしくお願いいたします」等の過剰敬語を使わない
- 定型の長文感謝（「ご指摘いただきありがとうございます。大変勉強になりました。」）を書かない
- 見出し（`#`）・水平線（`---`）・太字強調は使わない
- 鉤括弧「」を用語の強調や引用に多用しない。コード識別子はバッククォート、それ以外は裸で書く

## 悪い例／良い例

軽微な指摘（悪い例）：

```
🔍 **[nit]** タイムアウト値がハードコードされています

**理由**: 環境ごとに調整が必要になった場合、コード修正が必要となり保守性が低下します

**提案**: 以下のように環境変数から読み込む形にすることを推奨します
```

軽微な指摘（良い例。理由と要望を「〜ので、〜」で一文に融合する基本形）：

```
[nit]
タイムアウトが直書きだと環境ごとに変えられないので、環境変数から読むようにしたいです！
```

意図の質問（悪い例）：

```
**質問**: この実装ではリストをコピーしていますが、パフォーマンスへの影響を考慮した上での判断でしょうか。ご教示いただけますと幸いです。
```

意図の質問（良い例）：

```
[ask]
ここで毎回リストをコピーしてるのはなぜでしょうか？
浅い参照で足りるケースに見えていて、意図がわかっておらず、、
```

必須修正の指摘（良い例。診断は推量にとどめ、要求動詞は明確に）：

```
[must-fix]
filter結果が0件の時に`rows[0]`でエラー出そうなので、空の時は早期returnで対応して欲しいです！
```

同意して対応（悪い例）：

```
ご指摘ありがとうございます。おっしゃる通りかと存じますので、次のコミットで修正いたします。
```

同意して対応（良い例）：

```
確かにそうですね！
修正します！
```

対応報告（悪い例。hashを囲む・過剰敬語）：

```
ご指摘の件、以下のコミットで対応いたしました。
`a1b2c3d4`
ご確認のほどよろしくお願いいたします。
```

対応報告（良い例。hashは裸で、半角スペースを挟む）：

```
a1b2c3d4 で対応しました！
```

レビューへの反論（悪い例）：

```
ご指摘ありがとうございます。検討した結果、現状の実装を維持することとしました。理由は以下の通りです。
1. 既存の呼び出し元との互換性
2. 変更範囲の最小化
ご理解のほどよろしくお願いいたします。
```

レビューへの反論（良い例）：

```
おっしゃる通り可読性は下がるのですが、呼び出し元の互換を壊したくないので、このPRでは現状維持にしたいです！
リネームは別Issueを切って追うようにします。
```
