# Plan作成と適応的レビュー

## 前提

- PROJECT_ID: `~/.claude/scripts/project-id.sh` を実行して取得。取得できない場合は `default`
- Plan出力先: `~/.claude/context/<PROJECT_ID>/plans/<plan-name>/`
- plan.md / investigation.md の作成・修正はすべてオーケストレーター自身が直接行う。subagentに委託しない（文脈分断の防止。CLAUDE.mdの実装委譲ルールに対する意図的な例外）
- コード調査の使い分け: 2〜3ファイルで済む／中核判断に直結／パス候補が既知 → 自前Read。既存パターン探索／影響範囲洗い出し／5ファイル以上 → Exploreに委託し「事実の要約+パス」だけ受け取る

## 設計原則: 自己充足性

Planは常に「新しいセッションがplan.md（とinvestigation.md）だけを読んで実行に入れる」水準を保つ。plan作成後にセッションを切り替えて実装することが多く、**会話コンテキストは実装時に存在しない**前提で書く。ただし実コードをplanに書き込んで自己充足させるのではなく、事実・判断・コントラクト（インターフェイス）・手順の文書化で自己充足させる。実装の具体は実装フェーズ（/tdd等）で導出可能に保つ。

## 進行チェックリスト

以下をコピーして進行状況を追跡する：

```
Plan進捗:
- [ ] Step 1: 調査
- [ ] Step 2: plan.mdドラフト + 規模×リスク判定
- [ ] Step 3: review要否判定
- [ ] Step 4: review（ラウンドN、上限3）
- [ ] Step 5: 事実検証 → triage → 収束判定
- [ ] Step 6: ユーザー承認 + seed
- [ ] Step 7: 実装開始の確認
```

## Step 1: 調査

1. PROJECT_IDを取得し、タスク内容からkebab-caseのplan名を決定する
2. **同名planの存在チェック**: 出力先ディレクトリが既に存在する場合、続き（再利用）か別名で新規かをユーザーに確認する。planの使い捨て・重複作成は腐敗の主因（実測: 同一機能のplanが4回作り捨てられた例がある）
3. 出力先を `mkdir -p` で作成する
4. 現状把握を完了させる。推測でドラフトを書き始めない。観点: ユーザー要求の解釈（1〜3文で言い直す）／関連コード・ファイル／既存パターン・規約／影響範囲／制約・前提／過去資料（`~/.claude/context/<PROJECT_ID>/` 配下のADR・notes）／未解決の不明点

**investigation.mdの独立作成（条件付き）**: 以下のときのみ調査結果を独立ファイル `investigation.md` にする。それ以外はplan.md内の「調査結果」セクションで足りる（実測: 常時必須にした運用は実施率10%で形骸化した）。

- git運用系タスク（rebase・履歴改変・PR分割等。事実の正確さが成否を直接決める）
- 実機観察・ログ解析に由来するbugfix（観察事実と設計判断の分離価値が高い）
- Step 2で規模がmedium以上と判明し、かつ調査結果セクションが肥大した場合（このタイミングで昇格してよい）

## Step 2: plan.mdドラフト + 規模×リスク判定

plan.mdを以下の必須セクションで書く。**成果物にプロダクションコードが含まれる場合は、書く前に [references/tdd-plan.md](references/tdd-plan.md) を読む**（テストリスト・Interfacesブロックの規定がある）。

```markdown
# Plan: <plan-name>

## 状態
status: draft | in-review | approved | abandoned
<approved後は実装再開ポインタをここに書く（Step 6参照）>

## 目的
<1〜3文>

## 調査結果
<事実のみ。investigation.mdがある場合は「investigation.md参照」+要点のみ>

## 設計判断
<openな判断（複数の選択肢から選ぶ箇所）とその選択・根拠。会話で確定済みのものはここではなく決定済み事項リストへ>

## 決定済み事項リスト
<会話でユーザーと合意済みの判断・調査で確定した事実・意図的なスコープ外項目を列挙。
 reviewerへのインプットになる。なければ「なし」と明記（セクション自体は残す）>

## タスク分割
<タスク=コミット境界を基本とする。各タスクは独立して検証可能な成果物で終わる。
 コード系: タスクごとにテストリストとInterfacesブロックを付ける（references/tdd-plan.md参照）>

## 検証方法
<テストリスト / 手動検証手順 / 不変条件チェック（grep・SHA一致等）のいずれかを必ず書く。
 テストを書かない場合はその理由を明文化する>

## スコープ外
<やらないことを明示>
```

書き終えたら判定する：

**リスク判定**（1つでも該当すればreview必須）:
- git履歴の改変を含む
- 共有・本番環境の設定変更を含む
- 破壊的変更（スキーマ・公開API・外部公開物）を含む
- 失敗時の復旧手順が自明でない

**規模判定**: 「設計判断」セクションのopen件数を数える。0〜1件=small、2件以上=medium。ただし**会話で決定済みに移した判断が3件以上ある場合はsmall扱いにしない**（実質的な設計変更が判定をすり抜けるのを防ぐ。新鮮な目のレビューが誤りを拾う機会を残す）。

## Step 3: review要否判定

**スキップ可**: small かつ リスク該当なし かつ（TDD先行で完結する規模 or 前段でspec等がレビュー済み）
**判定に迷う場合**: フルレビューに倒すのではなく、AskUserQuestionで1問だけ確認して委ねる（境界的な軽作業を重い経路に押し込まない）
**それ以外**: Step 4へ

スキップする場合:
1. **スキップ理由をplan.mdの「状態」セクションに1行記録する**（例: `reviewスキップ: small・リスクなし・TDD先行完結`）。セッションを跨いだ事後監査を可能にするため
2. セルフレビューを実施する。検査項目: (a) ユーザー要求と各タスクの対応（要求の取りこぼしがないか） (b) 未定義参照（あるタスクが、どのタスクも定義していないファイル・シンボル・成果物に依存していないか） (c) テストリストの粒度（1項目=1振る舞いになっているか） (d) placeholder検出（「TBD」「後で決める」「適切に処理」等の先送り表現）
3. **セルフレビューでアプローチ変更級の問題（後述の目安参照）を検出した場合はStep 4に格上げする**（スキップ判定の自己修正）。問題なければStep 6へ

## Step 4: review（ラウンドN、上限3）

[references/review.md](references/review.md) の規定に従い、plan-reviewer agentを並列起動する。要点:

- コア2観点（戦略・実装系）は必ず起動。観点は排他的に定義されており、**実装系観点は成果物ドメインに合わせて差し替える**（コード／git運用／その他で観点が異なる。コード前提の観点を非コードplanに当てるとノイズになる）
- mediumでは追加観点1つ以上、リスク該当時はリスク観点を必ず追加
- reviewerにはplan.md・investigation.md（あれば）・ユーザーの元要求を渡す。plan.mdの決定済み事項リストが再議論の抑止として機能する
- reviewerはseverity（Blocker/Major/Minor）を自己申告する
- 出力先: `reviews/round-{N}/`

各ラウンドの冒頭で「現在Nラウンド目」と明記する。

## Step 5: 事実検証 → triage → 収束判定

1. **事実検証**: `reviews/round-{N}/` の全指摘を読み、事実関係が不明確なものはExploreを並列起動して検証する（実測: reviewerの指摘にはworktree取り違え・環境非互換等のfalse positiveが実在する。検証なしのtriageは机上の空論を採用する）
2. **triage**: 各指摘に adopted / rejected / partial / deferred を付与し、`reviews/round-{N}/triage.md` に記録する。**各行に実地検証メモ（何をどう確認したか）を添える**（実測: 検証メモ付きtriageのラウンドは棄却ゼロ・全採用の高品質に収束した）。Minorは一括で軽量処理してよい（実測: Minorの棄却率はBlockerの3倍以上）
3. **順序を固定する**: deferredをユーザーに確認して解決 → 全adopted確定 → アプローチ変更級判定。deferredから昇格したadoptedもアプローチ変更級判定を通す
4. plan.mdをオーケストレーター自身が直接修正する。新事実が判明したらinvestigation.md（あれば）も更新する
5. **収束判定**:
   - adoptedに**アプローチ変更級**が含まれる → Step 4へ戻る（次ラウンド）。**アプローチ変更級の目安**: タスク分割の境界／Interfacesの定義／採用アプローチ自体、のいずれかが変わった場合。reviewerが見たplanはもう存在しないため再レビューが必要
   - 詳細修正・文言レベルのみ → 修正箇所をセルフ検証してStep 6へ（実測: アプローチ変更級は初期ラウンドに集中し、3ラウンド目以降は文言修正とfalse positiveに収斂する）
   - 3ラウンドに達した → ユーザーに継続/打ち切りを確認

再レビュー時、前ラウンドの `reviews/round-{N-1}/` はreviewerに渡さない（全体を新鮮な目で見直させる）。追加観点の構成はラウンド1の選定を維持し、規模の再判定は次ラウンド起動時のみ反映する。

## Step 6: ユーザー承認 + seed

1. plan.md（とinvestigation.md）の**完全パス**（`...`で省略しない）と内容をユーザーに提示する。レビューを実施した場合は論点と対応のサマリーを添える
2. 承認を得たら「状態」を `approved` に更新する
3. **コード系planの場合、テストリストをseedする**: 各タスクのテストリストを実装順に連結し、`~/.claude/context/<PROJECT_ID>/test-lists/<plan-name>.md` に書き出す（整形規則は references/tdd-plan.md 参照）
4. **実装再開ポインタを「状態」セクションに書く**: 例 `実装再開時: /tdd に plan-name=<plan-name> を渡す（テストリスト: test-lists/<plan-name>.md）`。非コード系は `実装再開時: タスク分割セクションの順に実行` 等。セッションを切り替えても文書だけでハンドオフが閉じる

## Step 7: 実装開始の確認

「このセッションで実装を始めるか、ここで止めるか（セッション切替）」をユーザーに確認する。

- このセッションで開始・コード系: `/tdd` を起動する（seed済みテストリストがStep 1の成果物として採用される）
- このセッションで開始・非コード系: plan.mdのタスク分割の順に直接実行する
- 止める場合: 再開ポインタが書かれていることを確認して終了する

subagentへの実装委譲は本skillのスコープ外（将来の実装オーケストレーションskillで扱う）。

## 中断・再開

再開時は進行チェックリストと以下で位置を復元する：

- plan.mdが存在しない → Step 1から
- plan.mdの状態がdraftで `reviews/` がない → Step 3から
- `reviews/round-N/` があり `triage.md` がない → Step 5（そのラウンドのtriage）から
- triage.md済みで収束判定が未実施 → Step 5の5から
- 状態がapproved → Step 7（または実装再開ポインタに従う）

作業を打ち切る場合は「状態」を `abandoned` にして理由を1行残す（放置planと意図的な破棄を区別できるようにする）。

## 注意事項

- plan.mdに実装コード・テストコードを書かない。振る舞い（テストリスト）とコントラクト（Interfaces）までに留める。実装の詳細は/tddサイクルの中で決まり、planに書いたコードはインターフェイスが変わった瞬間に腐る
- 事実（調査結果）と設計判断のレイヤーを混ぜない。レビュー時に「事実誤認か判断ミスか」を切り分けるため
- plan lifecycle管理（古いplanの掃除等）はスコープ外
