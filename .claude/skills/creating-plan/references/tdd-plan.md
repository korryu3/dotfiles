# コード系plan規定（/tdd連携）

planの成果物にプロダクションコードが含まれる場合、SKILL.mdのStep 2でこのファイルを読む。

## 原則: planはテストコードを書かない

planに書くのは**振る舞い（テストリスト）とコントラクト（Interfaces）まで**。テストコード・実装コードは書かない。

理由: /tddはバッチごとに対象面（新規の公開面はスタブ）をコードに宣言してから、その対象面を叩くテストだけを書く。planのInterfacesはタスク間コントラクトのみで、タスク内部の公開面はバッチ開始時に決まる。planにテストコードを書くのは、その決定より前にシグネチャを固定する行為であり、バッチ開始時に腐る。振る舞いレベルに留めれば、インターフェイスが変わってもテストリストは有効なまま残る。

## タスクごとのテストリスト

タスク分割セクションの各タスクに、/tddのテストリスト形式（`- [ ]`）でそのまま書く:

```markdown
### Task 1: <タスク名>

テストリスト:
- [ ] 正常な入力で正しい結果を返す
- [ ] 空文字列を渡すとエラーを返す
- [ ] タイムアウト時にリトライする
```

粒度基準（/tddのStep 1と同一）:
- 書くのは**期待される振る舞い**。1項目=1振る舞い（「〜かつ〜」と書きたくなったら分割）
- 実装の設計判断（データ構造・デザインパターン・クラス分割）を混ぜない。それは/tddのStep 4（リファクタリング）の関心事

## Interfacesブロック（タスクごとに必須）

各タスクに、隣接タスクとの受け渡しコントラクトを書く:

```markdown
Interfaces:
- Consumes: <このタスクが先行タスクから使うもの。関数名・型・シグネチャ>
- Produces: <後続タスクが依存するもの。正確な名前・引数・戻り値の型>
```

理由: セッションを切り替えた実装者は自分のタスクの文脈しか持たない。隣接タスクが期待する名前と型を知る手段がこのブロックであり、自己充足性コントラクトの主担保。タスクが単一で完結する場合は `Interfaces: なし（単一タスク）` と明記する。

**境界の明確化**: planのInterfacesは「タスク間の受け渡し用シグネチャの確定」であり、/tddがStep 2（インターフェイス設計）・Step 4（実装設計）で行う設計活動を妨げない。タスク内部の実装・非公開の構造は/tddサイクルの中で自由に形成・リファクタしてよい（コントラクト層は厳密に、実装層は再生成可能に、の原則）。Produces宣言を変える必要が生じた場合のみplanに戻って更新する。Producesは/tddがバッチの対象面を宣言するときのシグネチャ供給源のひとつだが、網羅ではない。Producesに載らないタスク内部の公開面はバッチ開始時に決まる。

## テストを書かないケース

コードを触るplanでも、テストを書かない判断はありうる（例: 機械的rename、V1にもテストがない領域の文言修正）。その場合は検証方法セクションに**書かない理由と代替検証**を明文化する:

```markdown
## 検証方法
新規テストなし（理由: 機械的renameでロジック変更がないため）。
既存テスト336件のgreen維持と `yarn lint` で非回帰を確認する。
```

理由を書かずにテスト言及ゼロのplanは、意図的な省略か検討漏れかを後から区別できない。

## seed手順（Step 6承認後）

1. 各タスクのテストリストを**実装順に連結**する
2. 先頭に `# テストリスト: <plan-name>` ヘッダを付与する
3. タスク境界は見出しで保持する（/tddはタスク内でバッチ単位に `- [ ]` 行を選ぶため、タスク内の順序に依存しない。バッチはタスク境界を越えない）
4. `~/.claude/context/<PROJECT_ID>/test-lists/<plan-name>.md` に書き出す

```markdown
# テストリスト: <plan-name>

## Task 1: <タスク名>
- [ ] 正常な入力で正しい結果を返す
- [ ] 空文字列を渡すとエラーを返す

## Task 2: <タスク名>
- [ ] ...
```

`<plan-name>` はplanディレクトリ名と完全一致させる（/tddがこの規約でファイルを発見する）。

## /tddへの受け渡し

- seed後、plan.mdの「状態」セクションに実装再開ポインタを書く（SKILL.md Step 6の4）
- /tddはStep 1で同パスのseed済みファイルを検出し、Step 1の成果物として採用する（テストリストを再生成しない）
- 実装中に新しいテストの必要性に気づいた場合、/tddの規定どおりtest-listsファイルに追記される。plan.md側は凍結されたまま（実装時の真実源はtest-listsファイル）
