# テスト駆動開発（TDD）

Kent Beckが定義したTDDの5ステップワークフロー。
設計のやりすぎも、やらなさすぎも起こりにくくなるように考慮された、プログラミング中の構造化されたワークフローである。

## 前提

傾向として「まず実装を書いてからテストを追加する」方向に流れやすい。このスキルはその傾向を明示的に上書きする。実装コードを書きたくなったら、まずテストを書く。ただし型付きの未実装スタブ（本体は未実装例外）はインターフェイス宣言であり、この禁止の対象外。本体にロジックを書いた時点で対象になる。

### TDDと混同しやすい概念

- 自動テスト: テスティングフレームワークでテストを書くこと
- 開発者テスト: 開発者自身がテストを書くこと
- テストファースト: 実装より先にテストを書くこと
- TDD: テストリスト → レッド → グリーン → リファクタ → 繰り返し、という構造化されたワークフロー全体

「対象面（Step 2で定義）の外を叩くテストを先に書き溜めること（horizontal展開）」はTDDではない。
「設計をせずいきなりコードを書くこと」もTDDではない。

## 5つのステップ

テストリスト(1) → バッチのテストを書く(2:RED) → テストを成功させる(3:GREEN) → リファクタリング(4:REFACTOR) → 繰り返し(5)


### Step 1: テストリスト

実装に取りかかる前に、期待される振る舞いをリストアップする。

**書くもの**: 期待される動作（振る舞い）
- 正常系はこうなる
- サービスがタイムアウトしたらこうなる
- データベースにキーがまだないときはこうなる

**書かないもの**: 実装の設計判断
- 内部のデータ構造をどうするか
- どのデザインパターンを使うか
- クラスをどう分割するか

実装設計はStep 4（リファクタリング）で扱う。テストリストの段階で混ぜ込まない。

> よくある過ち：実装の設計判断を混ぜ込んでしまうこと。まあ落ち着こう。内部実装がどうあるべきか吟味する時間は後からいくらでも確保できる。

テストリストはファイルとして明示的に管理する。頭の中だけで管理しない。

#### テストリストの保存先

`~/.claude/scripts/project-id.sh` を実行してPROJECT_IDを取得し、以下のパスに保存する：

```
~/.claude/context/<PROJECT_ID>/test-lists/<plan-name>.md
```

`<plan-name>` は対応する Plan のディレクトリ名と一致させる。Plan がない場合はタスク内容から適切な kebab-case 名を決定する。

Plan作成skill（`/creating-plan`）が承認時にテストリストをseed済みの場合、このパスに既にファイルが存在する。**存在する場合は新規作成せず、そのファイルをStep 1の成果物として採用する**（テストリストを再生成・上書きしない）。進捗（`[x]`/`[/]`）を含む既存ファイルは「中断・再開時の注意」に従って読み、次に書く・実装すべきテストの把握から再開する。

#### テストリストの形式

```markdown
# テストリスト: <plan-name>

- [x] 正常な入力で正しい結果を返す
- [x] 空文字列を渡すとエラーを返す（付随GREEN: 前項の実装で満たされた）
- [/] タイムアウト時にリトライする  ← RED確認済み。次はこれをGREENにする
- [ ] 最大リトライ回数を超えたらエラー（Step 3で追加）
- [~] 並列リトライの上限 → 別planへ移動
```

マーカーは4状態：

| マーカー | 意味 | 更新タイミング |
|---|---|---|
| `[ ]` | 未着手 | — |
| `[/]` | 最後のRED実行で正しい理由により落ちたことを確認済み（テストコードあり、未実装） | Step 2のRED確認直後、バッチ分を一括で更新 |
| `[x]` | GREEN | Step 3でGREENを観測した直後。付随的に通った場合は行末に「付随GREEN」と注記 |
| `[~]` | 意図的な先送り | `→ 理由/移動先` を添える。`[/]`から落とす場合はテストコードを削除する |

マーカーの更新が済むまで次の作業に進まない。

### Step 2: バッチのテストを書く（RED）

テストリストから、ひとつの**対象面**を叩くテストを選び、まとめて実行可能なテストコードに翻訳する。書いたら1回実行し、**全件が正しい理由で失敗することをテストごとに確認する**。

#### 対象面を宣言する

**対象面** = このバッチのテストが直接呼ぶ、今回作る・変える公開面の集合。テストを書く前に宣言する。形は3つ：

| 状況 | 対象面の宣言 |
|---|---|
| まだ存在しない公開面 | **未実装スタブ**をコードに置く。関数名・引数・戻り値の型・エラー型を言語が許す範囲で型付けし、本体は必ず未実装例外にする。デフォルト値（`None`・`[]`・`""`等）を返さない |
| 既存の公開面のシグネチャを変える | シグネチャ変更だけ行い、本体は既存実装を維持する。未実装スタブで置き換えない |
| 既存の公開面の振る舞いだけ変える（バグ修正・仕様変更） | 対象面は変更対象の既存公開面。コードには何も置かない |

Planがある場合、シグネチャの供給源のひとつは `~/.claude/context/<PROJECT_ID>/plans/<plan-name>/plan.md` のタスク分割内Interfacesブロック（Produces）。ただし網羅ではなく、Producesに載らないタスク内部の公開面はここで決める。Planの有無で手順は変わらない。インターフェイスの設計指針は [references/interface-design.md](references/interface-design.md) を参照。

#### バッチ境界の判定

判定は1問：**「このテストが直接呼ぶ、今回作る・変える対象は、すべて今回の対象面の中にあるか」**。Yesなら同バッチ、Noなら次バッチ。対象面はコードに残る宣言（スタブ／変更対象のシグネチャ）なので、テストと照合できる。

対象面の規則：
- 1バッチの対象面は**1関数または1クラスの公開面**。`push`→`pop`のように対で意味を持つものは同一クラスの公開面として同じ集合でよい
- **対象面を決めてからテストを選ぶ。テストを集めてから対象面を広げない**
- **バッチはPlanのタスク境界を越えない**。越えたくなるのはタスク分割が誤っているサイン。タスク内に複数バッチは可
- バッチサイズ1は正当。バグ修正の再現テスト1本、未知ドメインの探索が典型

```
WRONG (horizontal): 対象面が未確定のテストまで先に書き溜める
  RED: test1, test2, test3, test4, test5   ← 複数の対象面にまたがる
  GREEN: impl1, impl2, impl3, impl4, impl5

RIGHT (batch): 1対象面のテストをまとめてRED、実装は1本ずつ
  stub(A) → RED: testA1, testA2, testA3 → GREEN: implA1 → implA2 → implA3 → REFACTOR
  stub(B) → RED: testB1, testB2         → GREEN: implB1 → implB2         → REFACTOR

RIGHT (vertical): batchの縮退形（バッチサイズ1）。対象面が1本分しか確定しないときはこれでよい
  stub(A) → RED: testA1 → GREEN: implA1 → REFACTOR
```

**バッチをまとめる理由**: 同じ対象面を叩くテスト群は同じインターフェイスに依存する。インターフェイスが変わっても書き直しは1対象面分に限定される。一方、対象面の外を叩くテストを先に書くと、実装過程でインターフェイスが変わったとき投機的に書いたテストを全部書き直すことになる。境界がchurnを封じるのではなく、1対象面に限定する。

#### REDの確認

1回の実行結果を1テストずつ読み、以下を確認する：

- 失敗理由が、**未実装**（対象スタブから出た未実装例外。スタックトレースが対象スタブを指す）または**対象の振る舞い未達**（アサーションの失敗）であること
- import/コンパイルエラー・タイポ・セットアップミスによる失敗ではないこと
- 実行された件数がバッチの本数と一致すること（絞り込み指定のミスによる収集漏れを検出する）
- **1件でも通ったら先に進まない**。テストが振る舞いを検査していないか、スタブがデフォルト値を返している

確認できたら、バッチ分のテストリスト項目を一括で`[/]`に更新する。

#### バッチ途中でシグネチャ変更が必要になったら

スタブ／シグネチャを変更 → 影響する`[/]`を`[ ]`に落とす → テストを修正 → バッチを再RED（1回実行、テストごと確認）→ 通過で`[/]`に戻す。期待値の誤りが判明した場合は実装出力に合わせず、テストリストの振る舞い定義から直す。

**やってはいけないこと**:
- 対象面の外を直接呼ぶテストをバッチに混ぜる
- アサーション（検証）のないテストを書く — カバレッジのためだけのテストはダブルチェックにならない

良いテスト・悪いテストのコード例は [references/tests.md](references/tests.md) を参照。

### Step 3: テストを成功させる（GREEN）

`[/]`から1本選び、プロダクションコードを変更して、そのテストを成功させる。実行はバッチ集合を絞り込んで行う（絞り込みができなければフルスイートでよい。往復回数は変わらない）。実行件数がバッチの本数以上であることを確認し、通ったテストを`[x]`にして次の`[/]`へ進む。

**付随的に通ったテスト**: 1本の最小実装で他の`[/]`も通った場合は`[x]`にして行末に「付随GREEN」と注記し、そのテストのGREENステップは飛ばす。最小実装を超えた実装をしたサインなので、Step 4で**実装**を見直す（テストは回帰の防波堤として残す）。

この過程で新しいテストの必要性に気づいたら、**テストリストファイルに追加する**（今はテストコードを書かない。次バッチ以降で扱う）。

**やってはいけないこと**:
- **バッチのテストをまとめて通そうとする**（実装を全部書いて1回実行） — 最小実装がインターフェイスを検査し、設計を創発させる。まとめて書くとその検査が起きない
- アサーションを削除・コメントアウトして成功したふりをする — 本当に成功させる
- テスト対象の実際の出力値をコピーして期待値にペーストする — ダブルチェックにならず、妥当性確認としての価値が失われる
- このフェーズでリファクタリングを混ぜる — 「帽子を2つかぶる」ことになる。まず動かし、それから正しくする。この分離が認知負荷を下げる。構造を変えたくなったら、そのテストをGREENにしてから帽子を替える（Step 4の途中リファクタ参照）

### Step 4: リファクタリング（REFACTOR）

バッチの全件が`[x]`になった状態で、コードを整理する。**ここで初めて実装設計の判断を行う。** 終わったらフルスイートを実行する。

#### ふたつの設計

設計には2種類ある：

1. **インターフェイス設計**: 振る舞いはどのように呼び出されるべきか — Step 2（対象面を宣言する段階）で扱う。[references/interface-design.md](references/interface-design.md) にテスタビリティの高いインターフェイスの設計指針がある
2. **実装設計**: システムはその振る舞いをどう実装すべきか — Step 4（リファクタリング段階）で扱う

この2つを同時にやらない。分離することで、一度にひとつの関心事だけに集中できる。

#### バッチ途中のリファクタ

基本はバッチ末だが、次のテストを通すために構造を変えたくなったらバッチ途中でやってよい。合格条件は「バッチ外の既存テストが全緑 ＋ バッチ内の`[x]`が維持されている ＋ `[/]`が引き続き落ちている」。

#### リファクタリングの注意点

- **重複は「指令」ではなく「ヒント」**: 重複を見つけたら自動的に除去するのではなく、設計改善のきっかけとして捉える。早すぎる抽象化に注意
- **モジュールを深くする**: インターフェイスは小さく、実装は深く。詳細は [references/deep-modules.md](references/deep-modules.md)
- **やりすぎない**: コードの整理整頓は気持ちがいいが、次のバッチに向かうのが怖いからといって過剰にリファクタリングしない
- **テストを壊さない**: リファクタリング前にグリーンだったテストがグリーンのままであることを都度確認する

### Step 5: 繰り返し

`[/]`が残っていなければ次のバッチへ。テストリストが空になるまで — あるいはコードの動作に対する不安が退屈に変わるまで — Step 2に戻る。

## サイクルの粒度

1バッチのリズムは「RED 1回 → GREEN n回 → REFACTOR 1回」。実行往復は旧来の1本ずつ（2N回）に対してN+2回になる。バッチは対象面で切るので、往復を減らすために対象面を広げない。大きなステップを踏もうとしたら、1本のGREEN実装をもっと小さく分割できないか考える。

## テストの品質

| 性質 | 良いテスト | 悪いテスト |
|------|-----------|-----------|
| **最小限** | ひとつの振る舞い。名前に「and」が入ったら分割する | `test_validates_email_and_domain_and_whitespace` |
| **明確** | 名前が振る舞いを記述する | `test_1`, `test_it_works` |
| **意図を示す** | 望ましいAPIを示す | 何をテストしているか不明 |
| **実コード** | モックは本当に不可避な場合のみ | すべてをモックで置き換える |
| **リファクタ耐性** | 内部実装を変えてもテストが壊れない | リファクタリングするとテストが壊れるが、振る舞いは変わっていない |

**モックのアンチパターン**: モックの追加やテストユーティリティの作成時は [references/anti-patterns.md](references/anti-patterns.md) を参照する。境界でのモック方針とDI設計は [references/mocking.md](references/mocking.md) を参照。

## ワークフロー外の注意

### テストより先にプロダクションコードを書いてしまったら

TDDワークフローの中では、テストが先。先にプロダクションコードを書いた場合、そのコードを「参考」として残すとテストが既存コードの追認になりやすい。TDDの効果（まだ存在しない振る舞いを定義すること）を得るには、先に書いたコードを手放してTDDサイクルで書き直す方が確実。

探索のために書いたプロトタイプがある場合も、TDDサイクルで書き直す。

Step 2で置く型付きの未実装スタブはこの注意の対象外。スタブはインターフェイス宣言であり振る舞いの実装ではないので、テストが既存コードを追認する事態は起きない。

### バグ修正

バグを見つけたら、まずそのバグを再現する失敗テストを書く。テストが失敗することを確認してから修正する。こうすることで、修正の証明と回帰テストの両方が得られる。

このワークフローでは、対象面は変更対象の既存公開面で、コードには何も置かない。再現テスト1本＝バッチサイズ1が典型。REDの正しい失敗理由はアサーションの失敗。

### 行き詰まったとき

| 問題 | 対処 |
|------|------|
| テストの書き方がわからない | 望ましいAPIを先に書く。アサーションから書き始める |
| テストが複雑すぎる | 設計が複雑すぎるサイン。インターフェイスを単純化する |
| 何もかもモックが必要 | コードの結合度が高すぎる。依存性注入を検討する |
| テストのセットアップが巨大 | ヘルパーを抽出する。それでも複雑なら設計を見直す |

## 完了前チェックリスト

作業完了を宣言する前に確認する：

- [ ] すべての新しい振る舞いに対応するテストがある
- [ ] 各テストがバッチのRED実行で正しい理由（未実装またはアサーション失敗。タイポやセットアップミスではない）により失敗するのを確認してから実装した
- [ ] 各テストに対して最小限のコードで成功させた（付随GREENになったものはREFACTORで実装を見直した）
- [ ] テストごとに実行してGREENを観測した
- [ ] すべてのテストがパスしている
- [ ] テスト出力にエラーや警告がない
- [ ] `[/]`が残っていない
- [ ] 未実装例外のまま残っているスタブがない
- [ ] テストリストが空になっている（または残項目を`[~]`にして理由を書いた）

## 中断・再開時の注意

テストリストファイルは常に最新の状態を保つ。中断時に特別な保存作業は不要（ファイルに書き出されているため）。

再開時はまずフルスイート（重い場合はテストリストが指す範囲＋直近バッチ）を1回実行し、結果でマーカーを補正する：

| 観測 | 補正 |
|---|---|
| テスト実体があるが`[ ]` | 正しい理由で落ちていれば`[/]`、通っていれば`[x]`（付随GREEN注記）、それ以外は`[ ]`のまま修正対象 |
| `[/]`だがテスト実体がない | `[ ]` |
| `[/]`だが通っている | `[x]`（付随GREEN注記） |
| `[x]`だが落ちる | マーカーは動かさず、回帰としてStep 3に戻って直す |

補正後、`[/]`が残っていればStep 3（GREEN）から、なければ次バッチのStep 2（RED）から再開する。新しいREDバッチは`[/]`を消化しきってから始める。seed済みリストはタスク内で厳密な上から順ではなく、今回の対象面に入らない項目は同タスク内の後続バッチへ送る。
